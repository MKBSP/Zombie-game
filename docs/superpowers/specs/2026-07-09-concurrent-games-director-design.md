# Concurrent games via a director + pool of single-match servers

**Date:** 2026-07-09
**Status:** Implemented (Phase 9).
**Scope:** Let the Railway deployment run **2–5 games at once** instead of one.

> **As-built refinement:** on-demand spawn + an idle-spawn timeout were replaced
> by a **warm buffer** (`WARM_CHILDREN`, default 1) of pre-booted children plus
> **dial-retry**. A freshly spawned Godot child needs a few seconds to bind its
> port, so dialing it immediately failed and closed the client ("server
> unreachable" on first host). Keeping a pre-booted child ready makes hosting
> instant; dial-retry covers cold spawns during startup/refill.

---

## Problem

The Railway server is the zombie game itself, run headless with `--server` — one
process, one Godot `SceneTree`. `scripts/network.gd` (autoload `Net`) holds a
single room's worth of module-level state (`_room_code`, `_members`,
`_zombie_peer`, `_shooter_peers`, `_match_started`) and `create_room()` refuses a
second host with *"A game is already running. Try Join instead."*

The deeper blocker is not that state: `_start_match()` calls
`get_tree().change_scene_to_file("res://scenes/world/world.tscn")` **on the
server itself**, and the world is fully server-authoritative — it simulates all
zombies/NPCs, uses a `MultiplayerSpawner`, sets per-peer authority on shooters,
and routes gameplay through `@rpc` calls guarded by `multiplayer.is_server()`.

Godot high-level multiplayer gives **one `multiplayer_peer` and one root
`SceneTree` per process**, and RPCs route across all connected peers. Two worlds
in one tree would cross-talk (a zombie command in game A would reach game B's
players). So "one process = one match" is baked deep and we do **not** fight it.

## Goal / non-goals

- **Goal:** Support up to ~5 concurrent, fully independent matches on one Railway
  service/domain, with the fragile server-authoritative game code left untouched.
- **Non-goals:** Matchmaking/ranking, autoscaling, cross-region fleets,
  reconnect-after-drop (still Phase D, unchanged). Anything past a handful of
  concurrent games is explicitly out of scope.

## Chosen approach

**One container + a director.** The public entry point stops being Godot and
becomes a small **Go** binary — the *director* — listening on Railway's `$PORT`.
It manages a pool of headless Godot `--server` child processes on internal
localhost ports; **each child runs exactly one room, then exits.** The director
picks/spawns the right child per incoming connection and reaps dead ones. All
game logic stays inside the Godot children.

Alternatives considered and rejected:
- **N standalone Railway services + HTTP matchmaker** — best isolation but ~5×
  idle cost and N+1 services/domains to manage. Overkill for 2–5 games.
- **In-process multi-world (per-branch `MultiplayerAPI` / per-peer visibility)** —
  a deep rewrite of the most fragile code (server-authoritative RPCs +
  `MultiplayerSpawner`) with high regression risk. Rejected.

## Components

### 1. Director (Go binary)

- **Raw TCP proxy** on `$PORT`. Railway terminates TLS at its edge, so the
  container sees plain traffic; the director never implements WebSocket framing.
  On each new connection it buffers and peeks the HTTP upgrade request line to
  read the query string:
  - `?host=1` → generate a room code; if the pool is under the cap, spawn a child
    seeded with that code on a free internal port; register `code → child`; splice
    the socket to it. If the pool is at the cap, close the socket (client surfaces
    a friendly "servers busy" via its existing `connection_failed`).
  - `?join=CODE` → look up the child by `CODE`; if a live child owns it, splice;
    else close the socket.
- Before forwarding, the director **rewrites the request line to
  `GET / HTTP/1.1`** (stripping the routing query it just read) so each Godot
  child sees a byte-identical handshake to today's single-server setup. All other
  headers (subprotocols, WebSocket negotiation) pass through verbatim.
- After routing, **splice bytes bidirectionally** (buffered prefix first) until
  either side closes. The director never parses or re-frames the WebSocket — the
  Godot ↔ Godot multiplayer handshake passes through untouched.
- **Registry & liveness:** `map[code] → { port, pid, spawnedAt }`. The **only**
  child→director signal is process exit: a child **exits when its room empties**
  (or after an idle-spawn timeout), and the director reaps the slot on exit. No
  side channel (no callback RPC/HTTP) is needed.
- **Pool cap:** default **5** concurrent children. Configurable via env
  (`MAX_GAMES`).
- **Idle-spawn timeout:** if a host connection is routed to a freshly spawned
  child but no Godot handshake/membership follows within **~20 s**, the director
  kills the orphan child. (Configurable via env.)
- **Room codes** are generated by the director (same alphabet/length as today's
  `network.gd`: 4 chars from `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`), making the
  director the single code authority. Collisions are avoided by checking the live
  registry before assigning.
- **Room-rule enforcement stays in Godot.** "Game full", "already started", and
  wrong-code-within-a-room are answered by the child's existing `_room_error`
  logic. The director only distinguishes "code maps to a live child" vs. not.

### 2. Godot child (small changes to today's `--server`)

Changes confined to `scripts/network.gd` server startup:
- Accept an **internal port** and an **injected room code** via CLI args, e.g.
  `-- --server --port=8912 --room=AB3K`, instead of reading `$PORT` and
  self-generating a code. Port arg overrides the `$PORT`/`DEFAULT_PORT` path;
  room arg pre-seeds `_room_code`.
- **Exit the process when the room closes** (`_close_room()` — i.e. room empty),
  so the director reaps. A **rematch keeps the room non-empty**, so the same
  child survives a rematch exactly as today — no UX change there.
- `create_room()` uses the **injected** room code instead of generating one, and
  drops the single-room *"a game is already running"* refusal (routing already
  guarantees one host per child). It still registers the sender as host
  (`_members[0]`) and replies `_room_joined(code)`, exactly as today — so the
  client handshake shape is unchanged.
- `join_room()` keeps its capacity/started/wrong-code checks and their
  `_room_error` messages; it now validates against the pre-seeded `_room_code`.

Everything else in `network.gd`, and all of `scenes/world/world.gd` and
`scripts/lobby_model.gd`, is unchanged.

### 3. Client + multiplayer menu

Intent must be known **at connect time**, so the old "Connect, *then* Host/Join"
step is folded into the Host/Join actions (`scripts/network.gd` client side +
the multiplayer menu UI):
- **Host** → `connect_to_server(base + "/?host=1")`; on `connected_to_server`,
  the client sends `create_room` as today and the child replies `room_joined(code)`
  with the director-injected code.
- **Join** → enter code → `connect_to_server(base + "/?join=" + CODE)`; on
  `connected_to_server`, send `join_room(CODE)` as today (child validates).
- The standalone "connect to server" action is removed (implicit in Host/Join).
- The lobby / role-claim / start / rematch client RPCs are all unchanged.

`connect_to_server(url)` already accepts a full `ws(s)://` URL, so appending the
query string is the only client-networking change. `PROD_SERVER_URL` and
`default_server_url()` are unchanged (they become the base the query is appended
to).

### 4. Local dev

- Default local dev runs the **director** too: `ws://127.0.0.1:8910/?host=1` etc.,
  director spawns children on `8911+`.
- A `--no-director` / direct path stays available for editor iteration: connect
  straight to a single child on `ws://127.0.0.1:8910` with a fixed room, matching
  today's `--autojoin --host/--join` local flow. This preserves the godot-ai MCP
  `project_run` loop without needing the Go binary in the editor.

### 5. Docker / Railway

- Multi-stage `Dockerfile`: a Go build stage compiles the director; the final
  image is today's Debian + Godot image **plus** the director binary.
- `CMD` runs the **director** (not Godot). The director spawns children with
  `godot --headless --path /app -- --server --port=<n> --room=<CODE>`.
- Still **one Railway service, one domain, one deploy**. `GODOT_VERSION` handling
  and the pre-import step are unchanged.

## Edge cases

- **Abandoned host:** connection routed to a fresh child but no membership within
  the idle-spawn timeout → director kills the orphan child.
- **Director crash:** all games drop; Railway auto-restarts the director. Kept
  deliberately simple to minimize this risk. (No cross-game blast radius beyond
  the shared container.)
- **Pool full:** host is refused at connect (socket closed → `connection_failed`
  on the client). Existing joiners are unaffected.
- **Resource ceiling:** the cap (5) bounds concurrent sims so one container's
  CPU/RAM comfortably holds them (small 2D sims).
- **Idle WebSocket disconnects** (~15 min Railway limit) are unchanged and still
  out of scope (Phase D reconnect).

## Web / itch.io client compatibility

Web playtesters on itch.io keep working, transparently:
- The web export connects with the **browser's native WebSocket** to
  `wss://…up.railway.app/?join=CODE`. Railway terminates TLS at its edge and hands
  the container a plain WebSocket upgrade, so **web and native clients look
  identical** to the director.
- The director routes on the request line, then splices raw bytes and rewrites the
  path to `/` (above), so each child sees an unchanged handshake. Nothing
  browser-specific is touched: HTML export, itch.io embed, SharedArrayBuffer, and
  the no-CORS-for-raw-WebSocket behavior are all unaffected.
- The only observable client difference (web or native) is the auto-built
  `?host` / `?join=CODE` query on the connect URL.

## Future-proofing / evolution path

The director is the correct long-term foundation, not a stopgap — it is the
standard "router + per-match allocator" pattern. The interfaces defined here (the
client `?host`/`?join=CODE` contract, one child = one match, the code registry)
stay stable as the system grows. Evolution is **additive**:
- **More concurrent games on one box:** raise `MAX_GAMES` until CPU/RAM limits.
- **Multi-host scale-out (beyond ~one container):** swap the director's
  "spawn a local child" step for "allocate from a fleet" (e.g. Agones/Nakama/VM
  pool); the client contract is unchanged.
- **HA director:** run multiple director replicas backed by a shared registry
  (e.g. Redis) instead of the in-memory map. Not needed at 2–5 games.
- **Matchmaking / reconnect (Phase D):** sit alongside the director, not replacing
  it.

Discipline: keep the director minimal now (single container, in-memory registry,
process-per-match). The scale-out pieces are YAGNI until real traffic demands
them.

## Testing

- **Director (Go unit tests, no Godot needed):** upgrade-line/query parsing;
  code generation + collision avoidance; allocation under the cap; refusal at
  cap; reap-on-exit; idle-spawn timeout; `join` to unknown vs. known code.
- **End-to-end (local):** start the director + drive two concurrent hosts →
  two children spawn on distinct ports, two independent matches run, and a zombie
  command / game-over in one does **not** affect the other (proves no cross-talk).
- **Godot child logic:** covered by existing `test/` scripts (run with the editor
  closed, per `CLAUDE.md` gotchas). `lobby_model.gd` tests are unaffected.

## Rollout

1. Build + unit-test the director in isolation (no Godot dependency).
2. Add the child CLI args (`--port`, `--room`) and exit-on-empty-room; verify a
   single child still plays a full match via the direct/`--no-director` path.
3. Wire the client Host/Join connect-with-intent flow + menu reflow.
4. Multi-stage Dockerfile; deploy to Railway; confirm 2 concurrent matches live.

## Open questions

None blocking. Tunables (`MAX_GAMES=5`, idle-spawn timeout ~20 s, internal port
base 8911) are defaults, adjustable via env without code changes.
